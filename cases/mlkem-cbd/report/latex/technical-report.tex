\newpageheading{2. Module and industrial context}{A real post-quantum cryptographic building block}
ML-KEM is the module-lattice key-encapsulation mechanism standardised in NIST FIPS 203. The evaluated module is the centred-binomial-distribution (CBD) sampler from the open \href{https://github.com/HWSec-CSIC/hope-mlkem}{HOPE-MLKEM} hardware implementation. It converts pseudorandom SHAKE bits into small positive and negative polynomial coefficients used as controlled mathematical noise.

This is one block inside ML-KEM, not a complete key-encapsulation engine. Its relevance is nevertheless concrete: it is synthesizable RTL from a real post-quantum design, with the state movement, modes and command behaviour expected in cryptographic IP.

\newpageheading{3. Architectural change}{Replace wide variable movement with fixed movement plus metadata}
The baseline stores 1,096 bits in \texttt{reg\_shake}. Each active cycle selects either a 16-bit or a 24-bit right shift according to \texttt{eta}. Generic mapping exposes this as a wide selection network around more than one thousand enabled flip-flops.

\begin{center}
\begin{tikzpicture}[node distance=8mm]
\node[font=\small\bfseries,text=Mid] (bt) {Baseline};
\node[input,below=6mm of bt,xshift=-44mm] (bs) {1,096-bit state};
\node[gate,right=12mm of bs,minimum width=34mm] (bm) {16 / 24-bit\\wide shift select};
\node[input,right=12mm of bm] (bo) {logical head};
\draw[signal] (bs)--(bm); \draw[signal] (bm)--(bo);
\node[font=\small\bfseries,text=GotherBlue,below=27mm of bt] (at) {Optimized};
\node[input,below=6mm of at,xshift=-44mm] (as) {fixed 24-bit\\chunk shift};
\node[accepted,right=12mm of as,minimum width=34mm] (ap) {two-bit\\byte phase};
\node[input,right=12mm of ap] (ao) {same logical head};
\draw[signal] (as)--(ap); \draw[signal] (ap)--(ao);
\end{tikzpicture}
\end{center}

The optimized RTL always moves physical chunks by 24 bits. A two-bit phase records the remaining byte offset needed to represent a logical 16-bit advance. This is analogous to retaining data in place and moving a read pointer instead of repeatedly moving the full data structure.

The public interface, addresses, output coefficients, completion cycle, reset, load, second-load, stalls and both eta modes remain unchanged.

The exact source change is published as \texttt{rtl/changes.patch}.

\newpageheading{4. Correctness contract}{Sequential behaviour, not only arithmetic equivalence}
The candidate passes three layers before any PPA metric is accepted:

\rowcolors{2}{Pale}{white}
\begin{tabularx}{\textwidth}{@{}B{36mm}Y B{20mm}@{}}
\rowcolor{Ink}\color{white}Gate & \color{white}Scope & \color{white}Result \\
Structure and lint & Verilator lint; Yosys module, interface, hierarchy and synthesis checks & PASS \\
Cycle regression & \FunctionalCycles{} cycles and \FunctionalChecks{} checks covering reset, eta 2/3, stalls, reload and second-load & PASS \\
Formal equivalence & EQY SAT five-step temporal induction after two reset cycles; complete joined 1,096-bit logical-state refinement & PASS \\
\end{tabularx}
\rowcolors{2}{}{}

Five-step induction is not a five-cycle bounded claim. The induction establishes an invariant for arbitrary future cycles after reset. Public outputs remain final obligations, and arithmetic temporaries are excluded as accidental match points.

\begin{scopebox}
\textbf{Formal boundary.} Equivalence uses two-state, defined-input hardware semantics after the declared reset. It does not claim identical Verilog X/Z propagation. The full archive contains the configuration, testbench and raw pass logs bound to the optimized RTL hash.
\end{scopebox}

\newpageheading{7. Evidence package}{A small review path with a deeper audit path}
The Git repository contains the before/after RTL, exact patch, compact certificate, report, checksums and a fail-closed Python verifier. A customer can check the complete compact package with:

\begin{lstlisting}
python3 verify.py
\end{lstlisting}

The separately downloadable raw archive contains all baseline and optimized timing and ACE power outputs for the 64 pairs, correctness logs, formal inputs, publication protocol and an internal hash manifest. Supplying it to the same verifier additionally re-extracts every primary metric:

\begin{lstlisting}
python3 verify.py --evidence-archive \
  mlkem-cbd-vtr45-full-evidence-v1.tar.gz
\end{lstlisting}

The compact verifier rejects altered RTL, patch drift, metric or score substitution, non-finite JSON, authority changes and incomplete manifests. Full-evidence mode also rejects unsafe archive paths, unexpected files, host paths, credential markers, failed routes and any raw metric that differs from the certificate.

\begin{scopebox}
\textbf{Audit meaning.} Raw-provenance verification checks the recorded files and re-derives the result; it does not rerun the EDA tools. A fresh external reproduction remains a separate, stronger review step.
\end{scopebox}

ML-KEM CBD is particularly relevant to teams implementing cryptographic FPGA/ASIC IP or preparing post-quantum migration. The case demonstrates an engagement pattern rather than a product claim: freeze one owned block and target, prove exact behaviour, measure an implementation objective and deliver auditable before/after evidence.

Cross-case percentages are not an apples-to-apples benchmark. Each circuit has its own interface, workload or activity model and implementation distribution. The supported claim is the paired improvement inside each frozen case.

\newpageheading{9. Limitations}{What the evidence does not establish}
This result does not claim:
\begin{itemize}
  \item ASIC synthesis, place-and-route or signoff;
  \item Vivado, Quartus or commercial-FPGA device performance;
  \item physical-board, measured-power, measured-energy or manufactured-silicon results;
  \item side-channel resistance, masking quality, constant-time software behaviour or fault resistance;
  \item security certification of HOPE-MLKEM or a complete FIPS 203 implementation;
  \item application-workload power, because ACE probabilistic activity is used;
  \item that the same state representation improves a different technology, architecture or integration context;
  \item accredited certification or independent third-party assurance.
\end{itemize}

The open PTM 45 nm FPGA proxy is useful for controlled relative experimentation. A customer pilot should replace it with the customer's implementation target, activity, constraints and signoff boundary.
